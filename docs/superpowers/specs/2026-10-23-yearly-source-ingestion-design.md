# 新年份数据自动引入设计

## 意图

维护者希望引入下一年河南专升本数据时，主要工作是提交当年官方网页链接；工具负责发现附件、下载、转换、建立分片索引并更新 metadata，前端不为新年份加分支。比少填几条链接更重要的是不把错年、缺专业或未经校对的数据发布给查询页。

2026 年的已知入口作为回放样例：

- 检索入口：`https://www.haeea.cn/govsearch?words=%E4%B8%93%E5%8D%87%E6%9C%AC&page=1`
- 一分一段页：`https://www.haeea.cn/a/202604/43664_744774c0.shtml`
- 省控线页：`https://www.haeea.cn/a/202604/43662_a29105c7.shtml`

这些是用户提供的来源种子，不代表当前环境已成功读取页面或验证附件；站点拒绝访问时应报错并停下，不用猜测结果补齐。

## 目标、边界与约束

- 每一年优先使用自己的专业对照；某年未取得专业对照时，不隐式借用最新版。旧年份目前的显式 `mappingReferences` 保持原样，新增年份缺对照则不发布。
- 年度输入保留“官方检索页 + 已知的精确公告页”以及必要时补充的明确链接。检索结果仅供发现候选，不是确认来源的证据。
- 年度输入还包括“招生高校及专业总表”，与后续分专业招生计划是不同来源、不同数据集：前者产生 `招生高校及专业_YYYY.json`，后者产生院校/专业计划人数，两者都纳入年度完整性验证，不互相替代。官方 PDF 可由 `www.haeea.cn` 或已核实的 `xcoss.henan.gov.cn` 提供；学校转载只作定位提示。
- 正常新增年份不修改 UI；使用现有 canonical JSON、`source-registry.json`、`refresh_catalog.py` 和 metadata 契约，继续产出 analytics、索引和按专业分片。
- 新增年份应全有或全无：来源不唯一、无法访问、附件缺失、OCR 待审、跨表冲突时保留现有 metadata 和线上可见年份不变。
- 原始 PDF、来源 URL、最终跳转 URL、哈希、解析结果、人工修正和审查结论应可追溯。不得因重新运行覆盖手工修正或既有年份的数据。
- 首阶段提供本地可复现命令和离线测试；GitHub Actions 在此命令稳定后复用它，生成待审查的变更，不自动合并。
- 不做全站盲爬、不用非官方镜像作为数据权威、不自动判定 OCR 疑难项、不把一分一段当作录取线预测。

## 方案选择

1. **全自动站内搜索并直接发布**：维护者最省事，但搜索命中、反爬和页面模板变化会造成错源或漏源，且不满足“出错就停”。不采用。
2. **所有 PDF URL 都由人逐项填写**：可控，但一个年份有大量专业分片，维护负担重。不采用作为常规流程；自动发现失败时可用精确链接覆盖。
3. **年度链接种子 + 严格发现和完整性校验**：维护者先给官方公告页，工具从页面发现附件；搜索只补充候选，候选不唯一即要求补精确链接。完整生成后以 diff 供人审查，再合并。采用此方案，因为它同时减少手工录入与静默发布错误。

用户已选定第三种方案，并确认“发现不唯一就停下补链接、生成结果经审查再合并”。下面的具体文件组织、命令和校验细节是实现建议，可在审阅本文时调整。

## 输入与发现

新增单个年度链接配置，例如 `data/year-links/2027.json`。字段包含 `year`、可选 `searchPageUrl`，以及按类型标记的官方公告页/精确附件链接：一分一段、省控线、招生计划、专业对照所需的代号表与对照表，以及招生高校及专业总表。已知链接可先填；未填者由官方检索页发现候选，但只有年份、标题、数据类型、官方来源均吻合且唯一时才选中，否则报告候选与缺项，请维护者补链接。不得从相近年份自动借用链接或专业对照。

先让发现器只产出可审查的来源清单，不改数据。每条记录至少有年度、类型、公告页、附件原始 URL、最终 URL、标题、文件名和 SHA-256。下载时验证最终跳转目标仍在允许的官方主机集合、响应是预期的 PDF/表格而非拦截页、文件非空且格式标识正确；不得仅信任清单中的 URL。镜像页最多协助定位官方链接，其自身不是可信来源。站点返回 403/412 或页面没有附件时明确失败，不把旧缓存冒充新年度结果。

沿用 `source-registry.json` 作为现有工具的执行登记册：新命令从经过确认的年度链接清单确定性地产生该年 `sources` 与 `crawlTargets` 项，保留既有年份条目。配置项只描述来源；输出路径按既有年度命名规则生成，避免同时手填链接和一组派生路径。重复运行同一输入应得到同一清单和生成文件。默认只允许新增年份；重新摄取已发布年份属于显式更新操作，并保留原始文件与生成物供差异审查。

## 转换、校验与发布

本地命令按以下顺序执行：

1. 读取年度链接配置，发现并下载官方附件，写来源清单和哈希。
2. 复用 `convert/sources.py` 的省控线、专业对照、招生计划 PDF 解析，以及现有一分一段 OCR/归一化工具。修正 `extract_cli.py` 对全新年度目标 JSON 必须已存在的假设；未校对 OCR 不进入发布阶段。
3. 在隔离的临时数据目录中形成该年的 canonical JSON、转换报告和拟增的 registry，运行统一发布前校验。
4. 校验通过后，运行现有 `refresh_catalog.py` 生成版本化 analytics、专业分片、索引和 catalog；最后原子替换 metadata。提交的变更包含链接配置、来源清单/原件或其可追溯记录、canonical JSON、报告、registry、派生文件及 metadata，交由人审查。

发布门槛必须显式验证：各类必需来源属于同一年且齐全；每年有自己的专业对照；专业代号/名称/分数线在对照、省控线、计划和分数段之间一致；没有重复或缺失的 PDF；省控线中的每个专业代号都有分数段，或有官方证明的“无分数段”例外；下载数、成功转换数、分片数与来源清单及例外数相符；报告无 blocking issue、待人工审核项或格式错误。历史年份的显式例外不自动套用到新年。已有 `refresh_catalog.py` 只检查分数段代号是省控线代号子集，需要把这一条件加强为有明示例外的覆盖校验。所有跨表特殊代号规则也应有测试和可审阅的例外记录，不以猜测补数据。

失败时不修改 `metadata/school-data.json`，不覆盖既有 canonical 或人工修正文件；未引用的临时/版本化文件可在下次运行安全复用或清理。现有 `refresh_catalog.py` 已把 metadata 放在版本化派生文件之后写入，应继续保留这个发布顺序。新年发布前的 staging 使前几步也不会把半成品暴露给 UI。

刷新 catalog 时，metadata 当前指向的 catalog 中记录了每个已发布年份的规范输入与报告哈希。若一个历史年份仍在 metadata 支持列表中，且这些输入哈希与当前完全一致，则保留该历史快照，不用新发布门槛追溯性地拒绝既有数据；任何新年份或发生变化的历史年份仍须通过完整的当前校验。这样既不把未证明的历史缺项伪装成“官方空表”，也不会因历史数据差异阻断新年发布。

## Actions 与审查界面

第一阶段先做本地命令及测试。第二阶段在 GitHub Actions 中对年度链接文件的 PR 运行同一命令：默认只进行发现、转换和校验并上传报告/生成 diff；如需由机器人产生生成数据提交，必须是待人工审查的提交或 PR，绝不自动合并，也不在来源或 OCR 不确定时生成貌似完整的 metadata。Actions 所需网络访问和官方站点反爬行为必须实测；若官方站点不可访问，显示具体失败链接与状态码。当前版本要求在线读取官方公告页及附件，离线附件导入尚未实现；未来如增加离线输入，也必须复用相同来源校验和发布链，不得绕过校验。

审查者至少能看到来源 URL 与哈希、新旧专业代号及数量差异、计划/省控线/分数段覆盖率、OCR 修正和例外、metadata 新增年份与前端资源路径。人确认这些差异后才合并。

## 验收与留给实现者的决定

- 用 2026 年已有文件离线回放并检查幂等；用合成 2027 年材料证明仅添加数据/链接配置就能让既有 UI 读到新年，不修改 JS。
- 候选公告两条、官方站点返回 412、缺一个专业 PDF、分片代号与省控线不一致、OCR 待审、无当年专业对照等案例均失败，且 metadata 字节不变。
- 正常流程的来源清单、registry、canonical JSON、analytics/index/shards 与 metadata 互相引用一致；复跑不抹去既有人工修正。
- `crawler`、`convert`、前端测试全部通过；Action 阶段额外验证最小权限、失败日志和待审查 diff。

实现者可以决定 CLI 模块名、报告 JSON 的内部结构和候选排序实现；不得自行放松来源、完整性及人工审查门槛。第一阶段不需要承诺官方站点永远可从 CI 抓取。
